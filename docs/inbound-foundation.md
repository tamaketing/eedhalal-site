# B2.5 Step 1 — inbound receipt foundation

Code and test database only. The Gate B2 n8n workflow is unchanged. These
endpoints do not dispatch AI, schedule retries, or send messages.

## Schema and privacy

Migration `004_inbound_messages` adds an independent receipt ledger. Existing
migrations remain immutable. UUIDs are generated by the service; timestamps
default to PostgreSQL `now()`. The runtime role `eedhalal_app` must exist and
must not own the table/schema: only SELECT/INSERT/UPDATE are granted. Run DDL
with the deployment role, never with the runtime role.

Transport data is immutable after receipt. Source event IDs are bounded to
128 characters and are not silently truncated. NULL retains no-dedup behavior.
Text (including CR/LF, quotes, tabs and emoji) is preserved exactly. PostgreSQL
cannot store NUL in TEXT; NUL is rejected explicitly. Message maximum: 32,000
JS string code units, within the existing API request body limit.

No arbitrary metadata, raw payloads, headers or reply tokens are accepted.
The reserved metadata column is always `{}`. Provider error details are
untrusted: stored detail is a fixed, bounded catalog description derived from
AI_RATE_LIMIT / AI_TIMEOUT / AI_PROVIDER_ERROR / AI_INVALID_RESPONSE. Supplied
error text is discarded, avoiding unreliable token-pattern redaction. Original
customer message text is data, not logging; it is never copied into audits.

## Service / API contract

All routes use existing Internal API Bearer authentication. No list/search
endpoint is included. Receipt returns `{ inbound, deduped }` (201 new, 200
duplicate); all other successful operations return `{ inbound }` (200).

| Method/path | Body |
| --- | --- |
| POST `/api/v1/inbound-messages` | `lineUserId?`, `channel?`, `messageType?`, `incomingMessage`, `sourceEventId?` |
| GET `/api/v1/inbound-messages/:id` | none |
| PATCH `/api/v1/inbound-messages/:id` | `customerId`, `expectedRevision` |
| POST `/api/v1/inbound-messages/:id/processing` | `expectedRevision` |
| POST `/api/v1/inbound-messages/:id/fail` | `expectedRevision`, `errorCode`, `errorDetail?` (discarded) |
| POST `/api/v1/inbound-messages/:id/retry` | `expectedRevision` |
| POST `/api/v1/inbound-messages/:id/complete` | `expectedRevision`, `draftId` (database UUID), `leadId?` |

Malformed input is 400, missing entity 404, stale revision/invalid transition or
conflicting linkage 409. Read the latest revision from the last successful
action or GET. Every mutation increments it; stale callbacks from before a
retry cannot alter a subsequent PROCESSING attempt (ABA protection).

Transitions: RECEIVED -> PROCESSING -> AI_FAILED -> PROCESSING (explicit retry)
or PROCESSING -> DRAFT_CREATED. Retry increments retryCount exactly once. No
automatic retry is implemented. DRAFT_CREATED is terminal for this service.
Customer attachment is allowed before completion, validates external identity
and cannot replace a different customer. Completion validates customer, source
event, exact incoming message, optional lead linkage and WAITING_FOR_HUMAN draft
status. It does not create, approve, edit or send a draft.

Each receipt/failure/completion/retry commits with its corresponding audit event.
Attach/processing update revision without additional audit types as approved.
Audits use SYSTEM/internal-api; caller-supplied actor fields are not trusted.
The current shared-secret API is not a distinct owner authentication system;
retry is an explicit trusted internal call, not proof of future console login.

Receipt uses the unique sourceEventId constraint, catching races outside the
rolled-back transaction. Duplicates return existing state without side effects.
Existing Lead/Draft idempotency remains unchanged. A partial existing lead is
reused by the existing Lead service; it is linked on inbound completion only.

## Test database and deployment boundary

Provision `EED_TEST_DATABASE_URL` for the test migration role and
`EED_TEST_RUNTIME_DATABASE_URL` for `eedhalal_app`, both addressing ONLY
loopback `eedhalal_test`. Do not derive these from production configuration.
Run PG suites serially (they explicitly clear test tables):

    node --test --test-concurrency=1 test/inbound-postgres.test.mjs test/postgres-integration.test.mjs test/persist-e2e.test.mjs

The new suite refuses any other database before executing SQL and uses a pinned
connection for migration transactions. Runtime permission tests always roll
back; no cluster role, ownership, or server authentication changes are made.

Memory/file adapters now serialize async transactions and roll back on callback
failure. File multi-table commits remain non-crash-atomic and single-process;
only PostgreSQL is the production durability target. Fake PG covers SQL shapes,
constraints and CAS, not real transaction rollback; real-PG tests are mandatory.

No production migration, API restart or workflow cutover is part of Step 1.
No historical receipts are fabricated for Gate B2 execution evidence. The
acknowledgement-before-persistence window and interrupted PROCESSING recovery
remain future cutover design items, not reliability guarantees of these routes.
