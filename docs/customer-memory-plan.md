## 1. ปัญหาที่ชั้น 3 แก้

ตอนนี้ก่อน AI ตอบลูกค้า บอทอ่านประวัติแค่ **4 รอบสนทนาล่าสุด** (ทดสอบกับลูกค้าที่คุยมา
33 draft → AI เห็น 4 รอบ) และอ่านจากตาราง `drafts` เท่านั้น → ข้อความที่ไม่เคยกลายเป็น draft
(44 ข้อความ) ไม่มีในความจำ AI เลย

**ผลกระทบจริง** (จากข้อความลูกค้าในระบบ):
- ลูกค้าบอกเบอร์โทรไว้แล้ว → บอทถามใหม่
- ลูกค้าขอใบกำกับภาษี → บอทไม่รู้ว่าเคยถามไว้
- บอก "มีคนทานเผ็ดไม่ได้ 1 คน" → บอทลืมไปตอนตอบใหม่
- สั่ง 18 กล่องวันนี้ → พรุ่งนี้บอทถามใหม่ว่าสั่งอะไร

**ชั้น 3 = ทุกครั้งที่บอทตอบ มันต้องรู้ "สถานะปัจจุบันของลูกค้าคนนี้" เสมอ**
ไม่ว่าคุยกันมานานแค่ไหน และไม่ว่าประวัติจะยาวเท่าไร

## 2. ข้อมูลที่เก็บ — ตาราง `customer_memories`

หนึ่งแถวต่อหนึ่งลูกค้า (เก็บสถานะปัจจุบัน + ประวัติงานที่ปิดแล้ว)

| คอลัมน์ | ชนิด | ความหมาย |
|---|---|---|
| `id` | UUID PK | |
| `customer_id` | UUID UNIQUE → `customers(id)` | ลูกค้า 1 คน = ความจำ 1 ชุด |
| `summary` | TEXT | สรุปสถานะปัจจุบันเป็นภาษาไทย (≤ 800 ตัวอักษร) |
| `facts` | JSONB | ข้อเท็จจริงที่ดึงได้ (ดูด้านล่าง) |
| `history` | JSONB | สถานะของงานที่ปิดแล้ว (เก็บ 5 รายการล่าสุด) |
| `status` | TEXT | `OPEN` = กำลังคุยเรื่องนี้ · `CLOSED` = งานนี้จบแล้ว |
| `source` | TEXT | `rule` = ระบบสร้าง · `owner` = เจ้าของแก้เอง (บอทห้ามทับ) |
| `rule_revision` | TEXT | revision ของ `data/business-rules.json` ตอนที่สร้าง |
| `created_at` / `updated_at` | TIMESTAMPTZ | |

### `facts` — ข้อเท็จจริงที่ต้องจำ (ดึงจากข้อความจริงที่ลูกค้าเคยส่ง)

| key | ตัวอย่างจริงจากแชทลูกค้า |
|---|---|
| `quantity` | 50 กล่อง · 18 กล่อง |
| `serviceType` | mealbox · buffet · snack |
| `menus` | ผัดไทยกุ้งสด · ข้าวหมกน่องไก่ · ข้าวผัดเนื้อ (ต่อวัน) |
| `eventDate` / `eventTime` | วันที่ 20 · 07.00 · 12.00 · 17.00 |
| `location` | ส่งสาทร · BITEC BANGNA · โรงพยาบาล · ห้วยขวาง |
| `budgetPerPerson` | 70 บาท/กล่อง |
| `phone` | 061-272-5989 |
| `taxId` / `needsInvoice` | Tax ID 0105558065167 · "ออกเป็นใบกำกับภาษีได้ไหม" |
| `dietaryNotes` | "มีคนทานเผ็ดไม่ได้ 1 คน" |
| `contactName` | คุณปิ่น |
| `openQuestions` | ยังไม่ได้ตอบ: เมนู / เวลา / ที่อยู่ |

> ทุก key มาจาก regex/กฎที่เขียนไว้ (**ไม่ใช่ AI**) → ไม่มีทางกุข้อมูลขึ้นมาเอง
> `openQuestions` คือสิ่งที่ร้านยังต้องถามลูกค้า เพื่อให้ AI ไม่ถามซ้ำและไม่ลืมว่าเคยถามแล้ว

## 3. วิธีสร้างและอัปเดตความจำ

### 3.1 กฎก่อน AI เสมอ (deterministic first)

```
ข้อความลูกค้าเข้ามา
   ↓
services/leads.mjs extractLeadSignals()        ← ใช้ซ้ำ ของเดิม
services/customerMemory.mjs extractFacts()      ← ของใหม่: วัน/เวลา/เมนู/ที่/เบอร์/ภาษี/เผ็ด
   ↓
mergeFacts(ของเดิม, ของใหม่)                  ← ของใหม่ทับ, แต่ของที่เจ้าของยืนยันแล้วล็อก
   ↓
buildSummary(facts)                             ← สร้างข้อความไทยจากแม่แบบ ไม่เรียก AI
   ↓
upsert customer_memories
```

### 3.2 `summary` สร้างแบบกฎ (ไม่เรียก AI) — เหตุผล

| ทางเลือก | ข้อดี | ข้อเสีย |
|---|---|---|
| **กฎ (แนะนำ)** | เร็วทันที ไม่กินโมเดล ไม่มีทางกุข้อมูล ตรวจสอบผลได้ตายตัว | ภาษาเป็นแม่แบบ (แต่อ่านเข้าใจได้) |
| ให้ AI เขียน | เป็นธรรมชาติ | เพิ่ม 2–3 วิ/ข้อความ, กุข้อมูลได้, แก้ยากกว่า |

ตัวอย่าง `summary` ที่ระบบสร้าง:
> "ลูกค้าขอข้าวกล่อง 50 กล่อง แบ่งเป็น 3 วัน (22–24 ก.ย.) เมนูผัดไทยกุ้งสด / ข้าวหมกน่องไก่ / ข้าวผัดเนื้อ
> ส่งที่สาทร งบ 70 บาท/กล่อง เบอร์ 061-272-5989 ต้องการใบกำกับภาษี — รอเจ้าของยืนยัน"

เจ้าของแก้ได้ทุกครั้งในหน้าประวัติลูกค้า (แล้วบอทจะไม่ทับ)

### 3.3 เมื่อไหร่ที่ความจำถูกอัปเดต

| เหตุการณ์ | ทำอะไร |
|---|---|
| ลูกค้าส่งข้อความใหม่ | ดึง facts ใหม่ → merge → สร้าง summary ใหม่ |
| เจ้าของส่งคำตอบจริง (draft → SENT) | อัปเดต `openQuestions` (ลบคำถามที่ตอบไปแล้ว) |
| เจ้าของแก้ summary เอง | `source='owner'` → บอทไม่ทับอีก (จนกว่าจะเริ่มงานใหม่) |
| เจ้าของปิดงาน (lead = WON/LOST) | ย้าย facts/summary ปัจจุบันเข้า `history` → `status='CLOSED'` |
| ลูกค้าทักมาใหม่หลังปิดงาน | เริ่มสถานะใหม่ (`status='OPEN'`) โดยเก็บงานเก่าไว้ใน `history` |

### 3.4 กฎ "ล็อกของที่เจ้าของยืนยัน"

ข้อมูลที่เจ้าของกรอกเอง (ชื่อบริษัท เบอร์ เลขภาษี ที่อยู่ เงื่องไขพิเศษ) ต้องไม่ถูกบอท
ทับด้วยการเดา จึงต้องมีที่เก็บ "เจ้าของยืนยันแล้ว" แยกจาก "บอทเดา"

> ทางเลือกที่ง่ายที่สุด: เก็บใน `customers` (ช่อง `phone`, `company_name`, `tax_id`, `address`, `notes`
> มีอยู่แล้ว) และให้ `customer_memories.facts` เก็บเฉพาะสถานะงาน — เจ้าของแก้ข้อมูลตัวเองใน
> `customers` ที่เดิม → บอทอ่านมาใส่ prompt ได้ แต่เขียนทับไม่ได้

## 4. การ inject เข้า prompt — จุดที่ AI "จำ" ได้

`tools/agent/line-chat.mjs` → `chatFacts()` เป็นจุดที่รวมข้อมูลอ้างอิงทุกข้อความอยู่แล้ว
เพิ่มบรรทัดเดียว:

```js
// ข้อมูลอ้างอิง (ยึดข้อมูลนี้เสมอ):
ขั้นต่ำออเดอร์ 10 กล่อง ต่อเมนูขั้นต่ำ 10 กล่อง
ราคาเริ่มต้นต่อกล่อง: Classic เริ่ม 65 บาท · Signature เริ่ม 155 บาท · …
เปิด จันทร์–เสาร์ 09:00–17:00
…
สถานะของลูกค้าคนนี้: <summary>          ← ของใหม่
ต้องการเพิ่มเติมจากลูกค้า: <openQuestions>  ← ของใหม่
```

**ผลลัพธ์:** บอทตอบเป็น "ครับ สั่ง 50 กล่อง แบ่ง 3 วัน ส่งสาทร ใช่ไหมครับ เดิมแจ้งเบอร์ไว้แล้ว
ใบกำกับภาษีทำได้ครับ" แทนที่จะเริ่มจากศูนย์ทุกครั้ง

> **ไม่ต้องเพิ่มความยาว prompt มาก** — เพิ่มราว 300–600 ตัวอักษร ต่อให้ AI จำข้ามเดือน

## 5. หน้าจอ Owner Console — "ประวัติลูกค้า 1 คน"

### 5.1 เข้าจากไหน

- คลิก **ชื่อลูกค้า** ในการ์ดของคิวข้อความ → เปิดหน้าประวัติลูกค้า
- เพิ่มแท็บ **"ลูกค้า"** ในเมนูข้าง → รายชื่อทั้งหมด + ค้นหา + จำนวนแชท

### 5.2 หน้าประวัติลูกค้า ประกอบด้วย

| ส่วน | เนื้อหา | การแก้ไข |
|---|---|---|
| **สรุปสถานะ** | `summary` + `facts` (อ่านง่าย เป็น bullet) | ✅ เจ้าของแก้ได้ (กล่องข้อความ) |
| **ข้อมูลลูกค้า** | ชื่อ LINE, ชื่อบริษัท, เบอร์, อีเมล, เลขภาษี, ที่อยู่ | ✅ แก้ได้ (คัดลอกจากในแชทได้) |
| **งานที่ตามอยู่ (lead)** | สถานะ, จำนวน, วันที่, ที่อยู่, งบ | ปุ่มเลื่อนสถานะ NEW → QUALIFYING → QUALIFIED → WON/LOST |
| **ประวัติแชท** | ทุกข้อความ + คำตอบ เรียงตามเวลา (ล่าสุดล่างสุด) | อ่านอย่างเดียว + ลิงก์ไป draft |
| **ปุ่มหยุดบอท** | หยุด/ต่อบอทรายคน | ✅ มีอยู่แล้วในระบบ แต่ยังไม่มีในหน้านี้ |
| **งานที่ปิดแล้ว** | `history` (สถานะงานก่อนหน้า) | อ่านอย่างเดียว |

### 5.3 เพิ่มใน API

| เมธอด | เส้นทาง | ทำอะไร |
|---|---|---|
| GET | `/api/v1/customers/:id` | โปรไฟล์ลูกค้า + memory + lead (ที่ยังไม่มี — ต้องเพิ่ม) |
| GET | `/api/v1/customers/:id/memory` | ความจำลูกค้า |
| PATCH | `/api/v1/customers/:id/memory` | เจ้าของแก้ summary/facts → `source='owner'` |
| GET | `/api/v1/customers/:id/thread` | ทุก draft + inbound ของลูกค้าเรียงตามเวลา (มี `/drafts?customerId=` แล้ว แต่ไม่ครบ inbound) |

## 7. ลำดับดำเนินการ (6 รอบ)

| รอบ | งาน | ไฟล์ | เวลา | ผลที่เห็น |
|---|---|---|---|---|
| **1** | ตาราง + adapter ทั้ง 3 + contract | 1–6 | 3 ชม. | ฐานพร้อม เทสต์ผ่าน |
| **2** | service: facts / merge / summary | 7, 15 | 3 ชม. | สรุปสถานะถูกต้องจากข้อความจริง |
| **3** | API + inject เข้า prompt | 9, 10, 11 | 3 ชม. | **บอทจำสถานะลูกค้าได้แล้ว** 🎯 |
| **4** | หน้าประวัติลูกค้าใน console | 12–14 | 5 ชม. | เจ้าของดู/แก้ได้รายคน |
| **5** | ย้อนข้อมูลเก่า → สร้าง memory ให้ลูกค้าเดิม | 7 (สคริปต์ย้อน) | 2 ชม. | ลูกค้า 26 คนมีความจำครบ |
| **6** | แก้ ① AI ล้ม → สร้าง draft สำรอง + ย้อน 44 ข้อความค้าง | gateway + สคริปต์ | 2 ชม. | **เจ้าของเห็นทุกข้อความ** |

> **รอบ 3 คือจุดที่ได้ผลทันที** — บอทจำสถานะลูกค้าได้ก่อนที่หน้าจอเสร็จ
> **รอบ 6 ควรทำคู่กัน** เพราะเป็นเรื่อง "เจ้าของเห็นครบ" ซึ่งเป็นครึ่งหนึ่งของคำถามเดิม

**รวม ≈ 3–4 วันทำงาน** (หรือ 2 วันถ้าทำรอบ 1–4 ก่อนรอบ 5–6)

### งานแถม (ทำได้ใน 15 นาที แนะนำทำพร้อมรอบ 3)

| ชั้น | แก้ตรงไหน | ผล |

| summary ยาวเกินแล้ว prompt บวม | จำกัด 800 ตัวอักษร + เก็บ `facts` เป็นโครงสร้าง (ไม่ใช่ข้อความยาว) |
| facts ขัดกันเอง (วันที่ 2 คนบอกคนละวัน) | ของใหม่ทับ + เก็บค่าเดิมไว้ใน `history` เจ้าของเห็นย้อนได้ |
| ข้อมูลเก่า (ก.ย.) ไม่มี memory | รอบ 5 ย้อนสร้างจาก draft ล่าสุดของแต่ละคน |
| เจ้าของแก้แล้วบอททับ | `source='owner'` → บอทไม่แตะจนกว่าจะเริ่มงานใหม่ |
| ข้อมูลส่วนตัวกระจายมากขึ้น | memory อยู่ในฐานเดียวกับที่อื่น ไม่มีไฟล์ใหม่ ไม่มีการส่งออกนอกเครื่อง |

**ตัวอย่างสรุปที่ AI เขียนให้ลูกค้าจริง**
> "คุณเบม 061-272-5989 แจ้งโอนค่าข้าววันที่ 20/10/69 แล้ว รอตรวจเงิน ส่งวันที่ 21/10/69 ศูนย์สิริกิติ์ 3 มื้อ ฮาลาล เช้า 07:00 กระเพราไก่+ไข่ดาว"

**ตัวเลขที่วัดได้**
- ลูกค้า 26 คน → มีความจำ 17 คน (อีก 9 คนเป็นแถวทดสอบจากเดือน ก.ย. ที่ไม่มีข้อความจริง)
- บอทเห็นบริบทเดิม 30 turn (เดิม 4) และเห็น "สถานะของลูกค้าคนนี้" ทุกข้อความ
- ข้อความที่ค้าง 40 รายการ (จากเดือน ก.ย.) เข้าคิวเจ้าของแล้ว
- ตัวตรวจ `node scripts/check-customer-memory.mjs` ผ่าน 14/14 · เทสต์เดิม 414 ผ่านหมด · PG จริง 36/36

### ข้อควรรู้

- **`customer_memories` ไม่มี foreign key ไปที่ `customers`** (migration 010) เพราะ PostgreSQL
  ไม่ยอม TRUNCATE ตารางที่มีตารางอื่นอ้างอิงถึง ซึ่งทำให้ชุดเทสต์จริงพัง ความถูกต้องกันลูกค้าหลอก
  ยังคงอยู่ที่ชั้น service (API ปฏิเสธถ้าไม่มีลูกค้า)
- **สรุปของเจ้าของไม่ถูกบอททับ** (`source='owner'`) จนกว่าจะกด "ปิดงานนี้"
- **AI เขียนเฉพาะสรุป** — ตัวเลขทุกตัวมาจากกฎ ไม่ใช่จาก AI
- **รอบ 5/6 เป็นสคริปต์** รันซ้ำได้ (ข้อมูลที่มีอยู่แล้วจะถูกข้าม)
