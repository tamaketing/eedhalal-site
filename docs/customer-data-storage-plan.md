# แผนเก็บข้อมูลลูกค้ารายคน (Customer data storage plan)

เอกสารนี้ตอบคำถามว่า "ข้อมูลการคุยของลูกค้าแต่ละคน เก็บไว้ที่ไหนดี" และเสนอทางที่เหมาะกับ
EED HALAL ตอนนี้ — ทั้งเรื่องที่เก็บ (system of record) และเรื่องที่สำรอง (backup)

> สถานะเอกสาร: **ขั้นที่ 1 เสร็จแล้ว** (2026-10-21) — ขั้นที่ 2–4 ยังไม่เริ่ม
> ผู้เกี่ยวข้อง: เจ้าของร้าน · อัปเดตล่าสุด 2026-10-21

---

## 1. ตอนนี้ข้อมูลอยู่ตรงไหน

ระบบ LINE รันบนเครื่องเจ้าของ ใช้ **file adapter** (`DB_ADAPTER=file`, `DB_DIR=data/line-runtime/`)

| ตาราง | ไฟล์ | แถวจริง | เก็บอะไร |
|---|---|---|---|
| `customers` | `customers.json` | 8 | โปรไฟล์ลูกค้า: lineUserId, ชื่อที่แสดง, เบอร์, อีเมล, บริษัท, เลขภาษี, ที่อยู่, หมายเหตุ, ปุ่มหยุดบอท |
| `inbound_messages` | `inboundMessages.json` | 87 | ข้อความดิบจาก LINE + รหัสเหตุการณ์ (กันส่งซ้ำ) |
| `drafts` | `drafts.json` | 84 | ข้อความลูกค้า + คำตอบที่ AI ร่าง + คำตอบที่เจ้าของส่งจริง + ประวัติสถานะ |
| `audit_logs` | `auditLogs.json` | 440 | บันทึกทุกการกระทำ (append-only) |
| `response_examples` | `responseExamples.json` | 18 | ตัวอย่างคำตอบที่เจ้าของอนุมัติแล้ว ให้บอทเรียนรู้น้ำเสียง |
| `leads` | `leads.json` | 0 | โครงการที่จับบอกได้ (ยังไม่เคยถูกเรียกจริง) |

**ข้อดีของที่เก็บปัจจุบัน:** เปิดอ่านได้ทันที ไม่ต้องตั้งค่าอะไร ไม่หลุดเครื่อง

**สิ่งที่ยังไม่พร้อม (ต้องแก้ถ้าจะใช้จริง):**

1. **ไม่มีการเชื่อมโยง** — `inbound_messages` ทั้ง 87 แถวยังอยู่สถานะ `RECEIVED` มี `customer_id = NULL`
   และ `draft_id = NULL` เพราะ gateway ไม่เคยเรียก `attachCustomer` / `completeInbound`
   (`services/inboundMessages.mjs` มีโค้ดพร้อมแต่ไม่ถูก wire) → ข้อความดิบกับแชทที่ร่างแยกกันไม่รู้ตัว
2. **Lead ไม่เคยถูกสร้าง** — `POST /api/v1/leads/evaluate` พร้อมใช้แล้ว (ดึงจำนวนคน/วันที่/งบ/ที่อยู่ได้)
   แต่ gateway ไม่เรียก → `leads.json` ว่าง แถว "ข้อมูลงานที่ตามอยู่" ใน Owner Console จึงไม่เคยมี
3. **ไม่มีหน้า "ประวัติลูกค้า 1 คน"** — Owner Console เป็นคิวแบนเรียงตามเวลา ต้องจำเองว่าใครคุยอะไร
4. **ไม่มีการเข้ารหัส ไม่มีการลบข้อมูลเก่า** — JSON ธรรมดา ไม่มี TTL เก็บทั้งชีวิต
5. **ไม่มีสำรองออกนอกเครื่อง** — ถ้าฮาร์ดดิสก์พัง ข้อมูลลูกค้าหายทั้งหมด

## 2. ทางเลือกทั้งหมด (เทียบกันตามจริง)

| ทางเลือก | เป็นระบบหลักได้ไหม | PDPA / ข้อมูลข้ามประเทศ | ค้น/กรอง/สรุป | ต้นทุน | ความเสี่ยง |
|---|---|---|---|---|---|
| **Google Drive** (โฟลเดอร์ JSON ต่อคน) | ❌ ไม่ได้ | ❌ เก็บนอกประเทศ | ❌ เปิดทีละไฟล์ | ฟรี | สูง: ไม่มี transaction ไม่มี FK แก้ย้อนหลังไม่ได้ และคนเดียวเห็นข้อมูลทั้งหมด |
| **Google Sheets** | ❌ ไม่ได้ | ❌ | ดูง่าย แต่ไม่มี transaction มี rate limit | ฟรี | สูง: แก้ทับกันได้ ไม่มี audit trail ตามแถว |
| **Airtable** | ⚠️ ได้บางส่วน | ❌ | มี UI ดี มีแอป | ~$10/เดือน | กลาง: API จำกัด, ไม่มี transaction, ต้องย้ายข้อมูลออกภายหลังได้ยาก |
| **Supabase** (Postgres managed) | ✅ | ❌ ต้องประเมิน | ✅ เหมือน Postgres | ~$25/เดือน | กลาง: dependency ต่างประเทศ, ต้องทำ DPA |
| **PostgreSQL บนเครื่องเจ้าของ** | ✅ | ✅ ในประเทศ | ✅ เต็มรูปแบบ | ฟรี (ติดตั้งแล้ว) | ต่ำ: ข้อมูลไม่ออกนอกเครื่อง, สำรองได้ |
| **PostgreSQL บน VPS ไทย** | ✅ | ✅ ในประเทศ | ✅ | ~200–400 บาท/เดือน | ต่ำ: ต้องดูแลเครื่อง, เหมาะถ้าจะรัน 24 ชม. |

### ทำไม Google Drive / Sheets ไม่ใช่ที่เก็บหลัก

- **PDPA พ.ศ. 2562:** ชื่อ เบอร์โทร เลขภาษี ที่อยู่ = ข้อมูลส่วนบุคคล การเก็บบน Google
  (เซิร์ฟเวอร์ต่างประเทศ) คือ "การส่งออกประเทศ" ต้องประเมินความเสี่ยงและแจ้งลูกค้า
  ถ้าไม่ทำ เสี่ยงโดนร้องเรียน — ไม่คุ้มกับความสะดวกที่ได้
- **ที่เก็บข้อมูลต้อง "เป็นฐานข้อมูล"**: ต้องกันส่งซ้ำ, ต้องรู้ว่าใครคุยกับใครเมื่อไหร่, ต้องแก้ย้อนหลังได้,
  ต้องลบลูกค้าตามคำขอได้ (ข้อกำหนด PDPA) — Drive/Sheets ทำไม่ได้
- **สิทธิ์การเข้าถึง**: บัญชี Google เดียว = คนเดียวที่เห็นข้อมูลลูกค้าทั้งหมด ไม่มี role แยก
- **ความเสี่ยงที่พบจริง**: Google Drive กู้ไฟล์เป็นเวอร์ชันก่อนหน้าได้ แต่ "ลบจริง" (PDPA
  right to erasure) ทำไม่ได้จริง → ข้อมูลลูกค้าที่ขอให้ลบ ยังอยู่ในประวัติการแก้ไข

### สิ่งที่มีอยู่แล้วในโปรเจกต์ (ทำต่อได้เลย ไม่ต้องซื้ออะไร)

- **PostgreSQL 17 ติดตั้งและรันอยู่แล้ว** บนเครื่องนี้ (`postgresql-x64-17`, พอร์ต 5432, auth แบบ scram-sha-256)
- **schema พร้อมแล้ว** 7 migration: `db/migrations/001_core.sql` → `007_customer_profile.sql`
  (customers, leads, drafts, inbound_messages, audit_logs, response_examples — พร้อม unique index, FK, CHECK constraint)
- **adapter พร้อมแล้ว**: `db/postgres.mjs` + ไลบรารี `pg` + `npm run db:migrate`
- **เทสต์ Postgres พร้อมแล้ว**: `test/postgres-integration.test.mjs`, `test/inbound-postgres.test.mjs`,
  `test/response-examples-postgres.test.mjs`

> สรุป: ทางเลือกที่มืออาชีพและถูกที่สุดสำหรับ EED HALAL คือ **ย้ายไป PostgreSQL ที่มีอยู่แล้ว**
> แล้วใช้ **Google Drive เป็นที่เก็บสำรองแบบเข้ารหัส** (ไม่ใช่ที่เก็บข้อมูลหลัก)
